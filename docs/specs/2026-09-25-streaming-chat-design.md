## 1. Purpose and success criteria

**What it proves:** streaming and a hand-built chat UI [D-chat-1]. Nothing else goes in; the other skills are separate projects [D-chat-1].

**Deliverable:**

- a live demo [D-chat-1]
- **time to first token (TTFT)** measured in production [D-chat-1], reported as the median of requests 2–15 [P: C-11], in the README headline [D-sec1]

**Size:** 8.5–12 h of work, about 1.5–2 days at ~6 focused hours per day [P]. That is inside the proposed 1–3-day target (template T-01). Section 11 corrects the earlier "1 day" estimate and says when to cut.

**Success criteria** [P]:

1. Within 60 seconds on the live demo, a recruiter can:
   - send a suggested prompt
   - watch the answer stream in
   - press Stop
   - press Regenerate
2. Stop cancels the model call in production, not just on screen. This is verified once by hand (section 9) and backed by an automated route test.
3. The README number comes from the same code path as the live on-screen caption. It is generated by a script, never typed by hand.
4. CI is green with no secrets and no model spend.

## 2. What the user sees

### 2.1 Empty state [D-S-02]

- A headline [P].
- One instruction line: `Try it: send a prompt → press Stop (or Esc) halfway → Regenerate`.
- Four suggested-prompt buttons that send immediately, with the approved wording:
  1. "200-word story about a lighthouse keeper"
  2. "Explain how HTTPS works to a new developer"
  3. "5 interview questions for a senior frontend engineer"
  4. "Follow-up email after a job interview"
- A muted line `N messages/hour per visitor; regenerations count`. N is `RATE_LIMIT_PER_HOUR` (template §5.3), passed as a prop from `app/page.tsx`, so the UI never states a wrong limit.
- Layout: one column on mobile, a 2×2 grid from `sm` up [P].

### 2.2 Conversation

**Rendering** [D-S-01]

- Assistant text is plain text (`whitespace-pre-wrap`), rendered token by token.
- The system instructions ask for plain text, never Markdown, of ~150–250 words. That leaves time to press Stop.
- An explicit length request from the user is honoured within the 1024-token cap, still in plain text [P].

**Composer** [P]

- A shadcn `Textarea` plus one button that swaps Send ↔ Stop while status is `submitted` or `streaming`.
- Stop has `aria-label="Stop generating"`.
- Enter sends, Shift+Enter inserts a newline, and Enter is ignored while `KeyboardEvent.isComposing` is true.
- `maxLength` is 2000 [D-S-03].
- Send is disabled for empty or whitespace-only input and while busy. Send and Enter are no-ops unless status is `ready` or `error`.

**Esc** stops from anywhere on the page, but only while busy [D-S-06].

**Typing indicator** [P]: three dots, shown while `submitted`, or while `streaming` before any text has arrived.

**After Stop** [D-S-06, D-S-23]

- The partial text stays, labeled **Stopped**.
- Focus returns to the textarea only when `matchMedia('(pointer: coarse)')` does not match, so Stop never opens the on-screen keyboard on touch devices [P].
- Stop before any non-whitespace text arrived: no empty bubble is shown. Instead, a row under the final user message reads **Stopped before a response · Regenerate**. This covers two cases: no assistant message exists yet, and one exists with empty text (Stop between `text-start` and the first delta [F: v7 check]).
- That row appears only when the user actually pressed Stop or Esc, tracked by `stoppedByUser`. It never appears after a timeout [D-S-22].

**Regenerate** [D-S-07]

- A text button shown only when status is `ready` or `error`, in exactly one place:
  - under the final message, when it is an assistant message with non-whitespace text
  - inside the "Stopped before a response" row, when the final message is a user message, or an assistant message with no non-whitespace text (the two cases of "After Stop"); `regenerate()` then slices off that empty assistant message [F: v7 check]
- Older assistant messages never show it.
- The placement is a pure helper, `regenerateSlot(messages, status, stoppedByUser)` in `lib/chat/ui.ts`, returning `'after-answer' | 'stopped-row' | null`. It returns `'stopped-row'` only when `stoppedByUser` is true; after a timeout, recovery goes through the generic banner's Retry [D-S-22].
- It replaces the answer, keeps no versions, and counts toward the rate limit.

**Cut-off label** [P]. When `finishReason === 'length'`, the answer is labeled `Cut at demo length limit`. It is expected to fire only when the user asks for more than the 1024-token cap (D-S-03) [P].

**TTFT caption** [D-S-10]. Each assistant message shows the muted caption `First token in N ms` once its first character arrives. The message element also carries `data-ttft-ms`.

**Autoscroll** [D-S-08]

- While following, a `ResizeObserver` on the content keeps the view at the bottom.
- Following stops at once on any of these [P for the exact gestures]:
  - an upward wheel
  - a touch-move that scrolls the content up (finger moving down)
  - PageUp, ArrowUp or Home pressed **outside** the textarea
  - a scroll event that lands more than 80 px from the bottom
- Following resumes at 80 px or less from the bottom, or when the user sends a message.
- A floating **Jump to latest** button appears while not following.
- Scrolling is instant while streaming. The Jump button scrolls smoothly unless `prefers-reduced-motion` is set [P].

**Header** [D-S-14, D-S-19]

- The model label, a **Mock model** badge in mock mode, and **New chat**.
- It follows the template attribute contract (template §5.6) on the header element:
  - `data-model`
  - `data-commit` (`VERCEL_GIT_COMMIT_SHA`, or `local`)
  - `data-mock`, which exists **only** in mock mode
- The measurement script reads these.

**New chat** [D-S-19 for the button; P for the reset steps]: awaits `stop()` if busy, then calls `setMessages([])`, clears the annotation map, the TTFT tracker and `interrupted`, and shows the empty state.

**Conversation cap** [D-S-03]: at 20 messages, the composer is disabled with the placeholder `Conversation limit reached. Start a new chat.` [P for the wording].

### 2.3 Error banners [D-S-05]

Error banners use shadcn `Alert` with `role="alert"`. There are exactly two variants:

1. **Demo limit.** Triggered when `APICallError.statusCode === 429`. It shows the server's text and has no Retry.
2. **Generic.** Text: `Couldn't get a response. Check your connection and try again.` [P for the wording]. It has **Retry**, which calls the same function as Regenerate.

The generic banner shows in two cases:

- status is `error`
- **`interrupted`** is true: the stream ended with no abort, no error and no finish reason, which is what a timeout produces [D-S-22]. `interrupted` is chat-level state and needs no assistant message, because a `firstChunkMs` timeout fires before `text-start`. It is cleared on the next send, regenerate, Retry or New chat.

### 2.4 Accessibility [D-S-20] — cuttable (section 11)

- The message list has `role="log"` and `aria-label="Conversation"`, with `aria-busy="true"` while busy.
- An `sr-only` `role="status"` region announces `Response complete`, `Response stopped` and errors. It never reads tokens aloud.
- Icon-only buttons have `aria-label`.
- Screen-reader behaviour is UNVERIFIED; this is a best-effort baseline.

### 2.5 Mobile (light) [P]

- An `h-dvh` column: header, scroll area, composer, and the footer as one muted line (template §5.5).
- The composer is padded with `env(safe-area-inset-bottom)`.
- Touch targets are 44 px.
- There is no autofocus on touch devices.
- It is checked manually on a real phone at 375 px (section 9).

## 3. Architecture

### 3.1 Server — `app/api/chat/route.ts`

The route runs on the Node runtime. It exports only `POST` and `maxDuration = 60` [D-S-04]. The pipeline:

1. **Rate limit.** Call `rateLimit(req)` from the template [D-chat-1], before parsing the body [P]. On denial, return `rateLimitResponse(result)` (template §5.3).
2. **Parse.** Run `req.json()` in a try/catch; failure returns `400 text/plain`.
3. **Validate and clean.** Call `validateAndClean(body)` (section 3.3); a rejection returns `400 text/plain`.
4. **Stream.** Call `streamText` with:
   - `model: getModel()` (template §5.1)
   - `instructions: SYSTEM_INSTRUCTIONS` — `system` was renamed in v7 [F: v7 check]
   - `messages: await convertToModelMessages(cleanMessages)` [F: v7 check]
   - `maxOutputTokens: MAX_OUTPUT_TOKENS` (1024) [D-S-03]
   - `reasoning: 'none'` [D-S-13; F: v7 check, values `'provider-default' | 'none' | 'minimal' | …`]
   - `abortSignal: req.signal` [F: v7 check]
   - `timeout: { firstChunkMs: FIRST_CHUNK_TIMEOUT_MS, chunkMs: CHUNK_TIMEOUT_MS }` (20 000 / 15 000) [D-S-04; F: v7 check]
5. **Respond.** Return `createUIMessageStreamResponse({ stream: toUIMessageStream({ stream: result.stream, onError: toSafeErrorMessage, sendReasoning: false }) })`.
   - `result.toUIMessageStreamResponse()` is deprecated in v7 [F: v7 check].
   - `sendReasoning` defaults to `true` in the source, so it is set to `false` explicitly [F: v7 check; D-S-13].

**Cancellation in production** [F: v7 check; ai-sdk.dev "stopping streams" and Vercel deployment guide]:

- `vercel.json` must contain `{ "functions": { "app/api/chat/route.ts": { "supportsCancellation": true } } }`. It works on the Node runtime only.
- Without it, the client stops rendering but the function and the model call keep running and billing. This corrects an earlier claim that `req.signal` alone was enough.
- With it, client `stop()` aborts the fetch → Vercel fires `req.signal` → `streamText` aborts the Gateway call.

### 3.3 Validation and cleaning — `lib/chat/validate.ts` [D-S-17, D-S-21]

`validateAndClean(body)` is pure. It returns `{ ok: true, messages }` or `{ ok: false, status: 400, text }`.

**Order** [P]. Shape and role checks run first, then the limits on the messages **as received**, then cleaning. Limits are not re-checked after merging, so a stopped-and-resent prompt never produces a 400.

**It rejects:**

- a `safeValidateUIMessages` failure [F: v7 check, returns `{ success, data | error }`]
- any role other than `user` or `assistant`
- a user message with a non-text part
- a user text over `MAX_USER_CHARS` (2000) [D-S-03]
- an assistant text over `MAX_ASSISTANT_CHARS` (6000) [P]. D-S-03's 2000 characters is read as the user-input limit, because an honest 1024-token answer exceeds 2000 characters. Assistant turns get their own cap so that a forged history cannot inflate input cost.
- more than `MAX_MESSAGES` (20), counted as the raw `messages.length`, the same count the client caps [D-S-03]

**It cleans:**

- drops non-text parts from assistant messages [P]. This deviates from D-S-17's "only text": honest assistant histories can carry non-text parts, and rejecting them would break normal use.
- drops assistant messages with no non-whitespace text (left by an early Stop)
- merges consecutive user messages into one, joined by a blank line [D-S-21]. They occur after an early Stop and after any failed request followed by a new message [F: v7 check].

**Defence in depth:** AI SDK 7 already rejects system messages inside `messages` by default [F: v7 check]. The role allow-list is input validation, not a prompt-injection defence.

### 3.5 Pure client logic — `lib/chat/ui.ts`

**`annotateFinish({ message, messages, isAbort, isError, finishReason })`** returns `{ id, stopped, cutOff, interrupted }`, following the verified `onFinish` behaviour [F: v7 check]:

- `message` is **never undefined**. On Stop before `text-start`, or on a transport error, it is an assistant message that was never pushed: a fresh id, `parts: []`, and absent from `messages`. This corrects an earlier assumption that it could be undefined.
- `stopped = isAbort`.
- `cutOff = finishReason === 'length'`.
- `interrupted = !isAbort && !isError && finishReason == null` [D-S-22].
  - A `firstChunkMs`/`chunkMs` timeout or a `maxDuration` cut ends the stream with an `abort` UI chunk, which `useChat` ignores.
  - Status ends as `ready`, with no error and no finish reason [F: v7 check]. This corrects an earlier claim that timeouts surface as errors.
  - The chat sets its chat-level `interrupted` flag from this value (section 2.3).

**`shouldSubmitOnKey({ key, shiftKey, isComposing })`**: true only for Enter without Shift and not composing.

**`describeChatError(error)`**: returns `'limit'` when `error.statusCode === 429` and `'generic'` otherwise. A non-2xx response makes the transport throw `APICallError { message: body, statusCode }` [F: v7 check]. The function never branches on message text.

### 3.6 TTFT tracker — `lib/chat/ttft.ts` and `hooks/use-ttft.ts`

```ts
export function createTtftTracker(now: () => number = () => performance.now()): {
  start(messages: UIMessage[]): void;
  observe(input: { messages: UIMessage[]; status: ChatStatus }): { id: string; ttftMs: number } | null;
  reset(): void;
};
```

- **`start`** stores `t0 = now()` and the ids of `messages`.
- **`observe`** returns a sample for the first message that meets all of these:
  - its id is not in that set
  - its role is `assistant`
  - its text parts total at least 1 character
- **Sample rules:**
  - at most one sample per id
  - `ttftMs = Math.round(now() - t0)`
- **Reset.** `observe` clears `t0` only on a busy → `ready`/`error` **edge**, not on every `ready` it sees (section 5.1).
- **Hook.** `useTtft(messages, status)` creates one tracker, calls `observe` on every commit, and returns `{ start, reset, ttftById: ReadonlyMap<string, number> }`. `MessageList` reads `ttftById` for the caption and `data-ttft-ms`.

## 4. Data flow

1. **Send.**
   - A prompt button or Enter calls `send(text)`.
   - `ttft.start(messages)` records `t0` and the current ids.
   - `sendMessage` appends the user message, and status becomes `submitted` [F: v7 check].
   - The button becomes Stop, following is forced on, and the typing dots appear.
2. **Request.**
   - The transport POSTs `{ id, messages, trigger, messageId }` [F: v7 check]; the server uses only `messages`.
   - The server runs rate limit → parse → validate/clean → `streamText` → SSE.
3. **Stream.**
   - The events arrive as `start`, `text-start`, then `text-delta`…
   - `useChat` creates the assistant message on `text-start` with a freshly generated id [F: v7 check: no assistant message exists before `text-start`, and ids are fresh on both submit and regenerate].
   - On the first commit where that new id holds at least 1 character, the tracker records `ttftMs`.
   - The autoscroll follows unless the user has scrolled away.
4. **Finish.**
   - `onFinish` runs `annotateFinish`, and status becomes `ready`.
   - The final assistant message shows Regenerate, the TTFT caption, and the Cut-off label if applicable.
   - `interrupted` shows the generic banner.
5. **Stop.**
   - `stop()` aborts the fetch, and status becomes `ready`. The partial text is kept [F: v7 check].
   - On the server, `req.signal` fires (with `supportsCancellation`) and the model call is aborted.
6. **Regenerate or Retry.**
   - `regen()` calls `ttft.start(messages)`, then `regenerate()`.
   - `regenerate()` slices off a trailing assistant message, or keeps a trailing user message, and re-sends [F: v7 check].
   - It throws `InvalidArgumentError` on an empty chat [F: v7 check]. The placement rules in section 2.2 prevent that case.
7. **Error.** Status becomes `error`, and `describeChatError` picks the banner. A mid-stream error keeps the partial text, and Retry replaces it.

## 5. The metric: time to first token

### 5.1 Definition [D-S-09]

TTFT is the time in milliseconds from `performance.now()`, taken just before `sendMessage()` or `regenerate()`, to the first React commit in which a **new** assistant message contains at least 1 text character. A new message is one whose id was absent when the request was sent.

- **It includes** the whole visitor path:
  - network (the request reuses the connection the page load opened, so TLS setup is not included)
  - function invocation
  - the Upstash check
  - validation
  - AI Gateway routing
  - provider queueing and prefill
  - any SDK retries (`maxRetries` defaults to 2 [F: v7 check])
  - SSE framing
  - the React commit
- **It excludes paint.** Whether the effect runs before or after paint is UNVERIFIED, so there is ±1 frame of uncertainty.
- **It deliberately does not use the `submitted → streaming` transition.** Status flips on `text-start`, before any character arrives [F: v7 check]. That transition would measure time to stream-open.

**Reset rule.** `t0` is cleared only on a busy → `ready`/`error` **transition**, so the reset is edge-triggered [F: v7 check]. `sendMessage` awaits file conversion before it pushes the message, so a commit can occur after `start()` while status is still `ready`. Clearing on every `ready` observation would drop the sample.

### 5.2 Measurement protocol [D-S-11]

**Command:**

```
MEASURE_URL=<production URL> MEASURE_LOCATION='<city, connection>' pnpm exec playwright test --project=measure
```

**Configuration.** `playwright.config.ts` adds the `measure` project **only when `MEASURE_URL` is set**. In that case:

- it omits `webServer`
- it sets `use.baseURL = MEASURE_URL`
- it sets `testMatch: /\.measure\.ts$/` and uses Desktop Chrome

The default `chromium` project keeps the default `*.spec.ts` match, so CI never runs `ttft.measure.ts`.

**The spec, `e2e/ttft.measure.ts`:**

- **Guards.** It refuses to run if `data-mock` is present or `data-model` is empty (attribute contract in section 2.2). It records `data-model` and `data-commit` from the deployed page, never from a flag.
- **Samples.**
  - 15 sequential requests, each a fresh single-turn chat in a fresh browser context.
  - The 4 suggested prompts are rotated by index.
  - Each request: click the prompt → wait for `data-ttft-ms` on the new assistant message → read it → click Stop (this saves tokens and exercises Stop in production) → wait 2 s.
  - The timeout is `test.setTimeout(5 * 60_000)` with `workers: 1`.
- **Early stop.** It stops at the first 429. An aborted run writes the JSON with `aborted: true`, prints no README lines, and exits non-zero.
- **Statistics** [P for the reporting rules]:
  - Request 1 is reported separately as "first request of the run". It is not called "cold", because Vercel Fluid Compute may reuse instances (UNVERIFIED).
  - Median, min and max are computed over requests 2–15 (n = 14).
  - There is no tail percentile below n = 20.
- **Quota.** 15 requests stay under 20/hour. Run it in its own hour, apart from manual testing.
- **Output.**
  - It writes `measurements/ttft-YYYY-MM-DD.json`: ISO date, URL, model, location, user agent, deployed commit, first-request ms, the samples, n, median, min and max.
  - It prints the two README lines of section 5.4. They are committed together with the JSON; the number is never typed by hand.

### 5.3 Calibration in CI, at zero cost [D-S-12]

- The mock's first token arrives after 600 ms.
- The e2e test asserts `600 ≤ data-ttft-ms < 2000`, so a pre-token (≈0 ms) or post-finish reading fails.
- The e2e test runs against a production build (template §7.2), so route compilation cannot blow the upper bound.
- `retries: 1` applies to this test only [P].

### 5.4 Reporting [P]

## 14. Amendments from the prototype (2026-09-26)

Before writing the implementation plan, a throwaway prototype of this spec was built and verified: lint, typecheck, 163 unit and route tests, build, and 22 e2e tests green in three consecutive CI-mode runs. The prototype showed that some statements above were wrong or incomplete. They are corrected here instead of being silently rewritten above (CLAUDE.md rule 6). Where an amendment conflicts with the text above, the amendment wins.

**Facts that correct the text above** `[F]`:

- **A-01 (§3.2).** The `[[error]]` fallback — a hand-written `ReadableStream` that calls `controller.error` — does **not** work. The HTTP body errors right after the `start` chunk, with no SSE `error` chunk and no `[DONE]`. The mock uses the V4 stream part `{ type: "error", error }` instead, which produces a proper `error` chunk. [F: ai@7.0.114, prototype experiment]
- **A-02 (§3.3).** `safeValidateUIMessages` is async, so `validateAndClean` returns a `Promise`. It is still pure. [F: ai@7.0.114 `dist/index.d.ts`]
- **A-03 (§3.5).** When Stop lands before `text-start`, the `onFinish` message that was never pushed has `parts: []` **or** `[{ type: "step-start" }]`. [F: @ai-sdk/react 4.0.117 source]
- **A-04 (§3.5, §6).** A `firstChunkMs` timeout is armed only after the provider responds (`doStream` resolves). The time spent before the provider's response headers, including the SDK's retry backoff, is bounded only by `maxDuration` (60 s). When `maxDuration` kills the function, nothing can write an `abort` chunk; the client instead sees a broken connection, which `useChat` reports as `status: "error"`, and the generic banner shows. On Vercel this path is UNVERIFIED. [F: ai@7.0.114 `stream-text` source]
- **A-05 (§4 step 2).** The POST body carries no `messageId` in this app, because it is `undefined`. [F]
- **A-06 (§5.1).** The "effect before or after paint" question is settled: `useChat` state comes through `useSyncExternalStore` (SyncLane), so the observing effect runs before paint. Drop the ±1 frame caveat. [F: @ai-sdk/react 4.0.117, react-dom 19.2.8]
- **A-07 (§3.1).** `streamText` logs errors with `console.error` by default. The route passes `onError: () => {}` to `streamText`, so each raw error is logged exactly once, by `toSafeErrorMessage`. A test pins this. [F]
- **A-08 (§8.3 test 3).** Playwright's `getByRole("alert")` already matches Next's route announcer on an empty page. The e2e suite therefore locates banners with `[data-slot="alert"]`. [F: Next 16.3.6]

  1. **A stop undone by a queued scroll** (§2.2 autoscroll, A-11). A stop intent (PageUp, an upward wheel, a touch move) that came between the last pin and that pin's scroll event, which fires only at the next rendering step, was undone by that event, and following resumed. `hooks/use-stick-to-bottom.ts` now records the scroll position at each stop intent and resumes only on a scroll that moves down; a scroll event that does not move the view never resumes it. Template commit `f5a6b86`; here "fix(chat): keep a stop gesture from being undone by a queued scroll". Pinned by the e2e "a scroll event queued before a stop by PageUp / wheel up / touch move down does not undo it".
  2. **A rotation while following** (§2.2 autoscroll). When a rotation made the text above the view take fewer lines, Chromium's scroll anchoring moved the view up, and a layout read before the next frame let that scroll event reach the hook before the resize observer pinned the view, so following stopped. The hook turns scroll anchoring off (`overflow-anchor: none`) while following, and back on while the visitor reads above the bottom, where it keeps their place. Template commit `e2b5bad`; here "fix(chat): keep a followed view pinned when a rotation rewraps the text above". Pinned by the e2e "touch: a rotation never moves a followed view up", which failed 5 of 10 runs before the fix and passed 10 of 10 after [F: local runs, 2026-09-30].
  3. **A long assistant text in the history** (§3.3, C-09). The client posts the whole history, and an honest answer can be longer than `MAX_ASSISTANT_CHARS` (6000): the mock's `[[slow]]` answer is 10,092 characters and can be stopped past the limit [F: `lib/ai/mock-scenarios.ts`; the e2e below], and a real answer cut at the token cap can run longer too [P: inference, template spec §14]. The route answered every later message with a 400 that Retry repeated until New chat. `validateAndClean` now cuts such a text to its last 6000 characters, never starting on the second half of a surrogate pair, instead of rejecting it; `VALIDATION_ERRORS.assistantTooLong` is removed. The model's input stays as bounded as with the 400, and the end is kept for a "continue" after a cut answer [D: template spec V-P8, 2026-09-30]. §8.1's "an assistant text of 6001 characters" and §8.2's "an oversized assistant turn → 400" become a cut to the end, with a 200. Template commit `df1a2d8`; here "fix(chat): cut a long assistant text in the history instead of a 400". Pinned by `validate.test.ts`, the route test "answers a history with an assistant turn over 6000 characters, cut to its end for the model", and the e2e "4. a follow-up after an answer longer than MAX_ASSISTANT_CHARS" (a completed `[[slow]]` answer, one stopped past the limit, one cut at the length limit).
  4. **The focus after New chat at the cap** (§2.2 "Conversation cap", A-14). At 20 messages the composer is disabled until New chat's commit, and `focus()` does nothing on a disabled control, so New chat left the focus on its own button. The focus now runs in an effect after that commit. Template commit `df1a2d8`; here "fix(chat): focus the composer after New chat at the message cap". Pinned by the cap e2e (the composer is focused and typing lands in it), "at the cap, New chat from the keyboard puts the focus in the composer", and a focus check after New chat below the cap.
